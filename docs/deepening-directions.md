# 可以深入做的方向

这份文档整理 Ollupi 下一步值得做深的地方。每一项都写了现状在代码里的位置，方便核对。

总的判断：Ollupi 现在不缺功能，缺的是把一个难题做到底，以及证明它可靠的证据。`docs/agent-capabilities.md` 里还有不少项标着"无"或"部分"，但照着补文件编辑、终端界面、插件这些广度项，只会让它更像一个缩水版的 Claude Code，不会增加深度。下面的方向都是往"正确性、可验证、可运维"上做，而不是加功能。

项目本身不带测试（见 README），所以下面说的"怎么证明做对了"都是指单独的验证工具或一次性的验证程序，不进仓库的常规代码。

## 总览

| 序号 | 方向 | 规模 | 优先级 |
| --- | --- | --- | --- |
| 1 | 崩溃一致性与工具副作用 | 大 | 最高 |
| 2 | 确定性回放与回归评测 | 中 | 高 |
| 3 | 调度、限流、重试和背压 | 中 | 中 |
| 4 | 可观测性：链路追踪、指标、费用 | 中 | 中 |
| 5 | token 估算的误差统计 | 小 | 低 |
| 6 | 长会话的读取成本 | 中 | 低 |

建议顺序：1 → 2 → 3 → 4 → 5 → 6。

## 1. 崩溃一致性与工具副作用

这是最值得做深的一项，因为它本质上是一个分布式系统问题，而且 Ollupi 已经有了大部分基础：每一步先落库，再执行。

**现状。** 进程在工具执行中途崩溃，重启后 `repo.RecoverItems`（`repo/items.go`）会把这次调用标成失败，错误写的是"the app stopped while this call was being handled; it may or may not have taken effect, so check before repeating it"。这个处理是诚实的，但等于把"到底执行了没有"这个问题交给了模型和用户。对拨电话、写 Excel、发消息这类有副作用的工具，模型很可能直接重试，造成重复执行。

另外，`tools.Annotations` 已经有 `IdempotentHint` 字段，但运行时没有任何地方读它。

**做法。**

先把每次工具调用拆成明确的阶段：已批准、已开始（意图已落库）、已完成或已失败。"已开始"这条记录要带一个幂等键，由 thread、turn 和 item id 派生，在批准时就固定下来，重启后不变。

工具按副作用分三类，由工具自己在 `tools.Spec` 上声明：

- **只读或幂等**：重启后可以直接重跑。
- **可核对**：工具实现一个核对函数，运行时把幂等键交给它，问"这次调用生效了没有"。比如写 Excel 的工具可以检查那一行是不是已经写成了目标值；对接外部 API 的工具把幂等键作为请求的 idempotency key 发出去，核对时去查。
- **不可核对**：保持现在的处理方式，标成"结果未知"，但要在记录里明确区分"未知"和"失败"，不让模型把"未知"当成"失败"去重试。

重启恢复时按类别处理：幂等的重跑，可核对的先核对再决定是补记结果还是重跑，不可核对的交给用户。

**怎么证明做对了。** 故障注入：在每一个落库点前后杀掉进程，然后重启、恢复，检查两个性质：

- 声明了幂等或可核对的工具，副作用最多发生一次；
- 每个 turn 最后都处在明确的终态，不会卡在进行中。

**规模。** 大。涉及 `repo`（状态和恢复）、`agent/runtime`（执行阶段）、`tools`（新的声明）和 `agent`（恢复流程）。

## 2. 确定性回放与回归评测

**现状。** 每条模型响应、每次工具调用、每个审批和提问都已经落成 item，`agent/contextmanager` 按设计只依赖这些 item 来渲染 prompt（为了服务商的前缀缓存，system 和工具列表固定、对话只追加），但"同样的 item 一定渲染出同样的 prompt"没有任何验证。缺的是一个能拿记录重跑的执行器。

**做法。**

回放器由两部分组成：

- 一个本地的假模型服务（`*llm.OpenAI` 指向它即可，模型客户端不是 interface）：按顺序返回记录里的模型输出；同时检查这次发来的 prompt 和当时记录的是否一致，不一致就报告第一处差异。注意脱敏占位符带进程随机密钥，比较前要先还原或按同一进程重放。
- 一个假的工具提供者：按记录返回工具结果，不真的执行。

用它重跑一个录下来的会话，检查工具调用序列、审批决定和最终状态是否和原来一致。以后改上下文压缩、脱敏规则、权限规则或 prompt 模板时，能直接看出哪些已有会话的行为变了。

再往上一层是评测：维护一批录下来的会话作为样本集，改动前后各跑一遍，统计工具调用次数、token 用量、任务是否完成这些指标的变化。这里需要真的模型，所以不是确定性的，要单独跑。

**规模。** 中。主要是新代码，基本不需要改已有逻辑。做完之后，README 里"整个会话可以完整审计"可以改回"可以回放"。

## 3. 调度、限流、重试和背压

**现状。**

- `agent/loop.go`：所有 thread 共用一条全局 FIFO 队列，并发上限写死成 `workers = 4`。
- `pkg/llm/openai.go`：创建 openai 客户端时没有设置任何重试或退避选项，失败重试完全依赖 openai-go SDK 自带的默认行为，Ollupi 自己没有策略。
- `agent/runtime`：每个 turn 的上限写死成模型调用 200 次、工具调用 400 次、连续失败 10 次。
- 网关的每个连接的发送队列有 16 MiB 上限，超出就断开这个连接；这是背压的最后一道防线，不是限流。

**做法。**

- 并发上限和每个 turn 的上限改成可配置项，默认值不变。
- 按模型连接做令牌桶限流；收到 429 时按 `Retry-After` 退避，其他可重试错误用带抖动的指数退避，重试次数和总时长都有上限，而且每次重试都落成记录。
- 调度从全局 FIFO 改成按 thread 公平轮转，避免一个会话连续派生很多子代理时饿死其他会话。

**怎么证明做对了。** 用一个可以设置延迟和 429 比例的假服务商做压测，报告吞吐和排队延迟的 p50、p99，以及限流前后的对比。

**规模。** 中。

## 4. 可观测性

**现状。** 每次模型调用和工具调用的 token 用量、上下文统计都记在 item 上，但只能逐条去看，没有聚合，也没有对外导出。

**做法。**

- 用 OpenTelemetry 打 span：turn、每次模型调用、每次工具调用、审批等待，作为一棵树。子代理的 turn 挂在父 turn 下面。
- 指标：排队时长、模型首字延迟、工具耗时、失败率、每个 turn 的 token 数。
- 按模型连接配置单价，算出每个 turn 和每个会话的费用。
- 导出接口做成可选的，库本身不强依赖某个后端。

**规模。** 中。

## 5. token 估算的误差统计

**现状。** `pkg/llm` 的 `EstimateTokens` 是一条启发式规则：ASCII 字符每 4 个算 1 个 token，每个非 ASCII 字符算 1 个 token。`contextmanager` 用记录里的真实用量校准：上次压缩之后有同一模型的请求时，用它的真实 prompt tokens 加上估算增量；刚压缩完时，用压缩请求（或更早请求）的"真实值 ÷ 估算值"比例放大估算，比例不低于 1。

**做法。** 用已有记录算出估算值和真实值的误差分布，按模型和语言分开统计。如果误差大，再按模型给估算加系数，或者接入对应模型的分词器。

**规模。** 小。数据现成，结论具体。

## 6. 长会话的读取成本

**现状。** 没有内存缓存，每次读都查库（见 README"暂时没有缓存"）。`repo.DB.Thread` 每次返回一个会话的全部 turn 和 item，而编排器在一次迭代的前后、结束 turn、推送状态时都会重新读整个会话，长会话的每一步都是 O(item 数) 的读取，还会重复好几次。

**做法。** 先量：记录每次迭代读了几次会话、读了多少行。再按需要只读当前 turn 和上次压缩之后的 item（压缩点之前的内容已经由压缩摘要代替），或者在一次迭代内复用同一份读取结果。

**规模。** 中。在会话真的变长之前，优先级最低。

## 不建议现在做的

文件读写和编辑、搜索、终端界面、IDE 插件、插件系统、斜杠命令这些，都是能力清单里的广度项。它们有用，但其他 agent 都已经做得很成熟，补上之后 Ollupi 也只是"又一个有这些功能的 agent"，体现不出深度。等上面几项做完、核心可靠性有了证据，再按应用的实际需要来补。
